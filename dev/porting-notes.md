# TOFU65 3.0 유선 ZMK 포팅 기록

2026-10-29 기준. 순정 소스나 회로도를 전제로 하지 않고, 사용자가 기판에서 읽은 UF2와 실기기 관찰에서 출발한 기록입니다. README는 설치·사용 안내, 이 문서는 이식 과정과 판단 근거를 담당합니다.

## 1. 참고한 저장소와 적용 범위

- `../zmk-Owlab_Link/README.md`, `README_ko.md`, `docs/porting-guide_ko.md`: 영문/한국어 README, 검증 빌드 표, 부트로더 보존, 클럭·시작 상태·스캔 타이밍을 각각 확인하는 접근.
- `../zmk-neo_neo65cu/README.md`, `README_ko.md`, `dev/porting-notes.md`: 근거 → 구현 → 실패 → 실기기 결과 기록, 기본 하드웨어 키맵과 개인 키맵 분리, Fn 레이어 부트 진입.
- 참고 저장소는 읽기 전용으로 사용했습니다. LINK65의 `0x08006000` 오프셋, HSE 72 MHz, 일반 GPIO 매트릭스, Neo65 CU의 STM32F072 ROM 진입 주소·DFU 명령은 가져오지 않았습니다.
- TOFU의 전달 형식은 UF2 저장장치 복사입니다. 다른 저장소의 dfu-util Windows 플래셔나 Release 기능이 구현됐다고 표시하지 않습니다.

## 2. 보존 조건과 최초 증거

원본 `uf2 storage/CURRENT.UF2`는 변경하지 않습니다. SHA-256:

```text
b57f555568536f6ade812e9065394af00b2229ca8fcc27965ae802ff369d99f0
```

`INFO_UF2.TXT`는 `ARM32F103-UniCore-F1-v1.x`, 부트로더 `v24.07.23i`를 보고합니다. 이는 실제 칩 제조사 마킹을 대신하지 않습니다. 스냅샷 512블록에서 추출한 플래시 데이터는 128 KiB이며, 파일 헤더·번호·주소 연속성을 검사했습니다.

| 영역 | 범위 / 처리 |
| --- | --- |
| 부트로더 | `0x08000000`–`0x08003FFF`, 일반/복구 UF2 모두 제외 |
| ZMK 앱 | `0x08004000`–`0x0801DFFF`, 최대 104 KiB |
| 순정 설정 | `0x0801E000`–`0x0801FFFF`, 일반 ZMK 업로드에서 보존 |
| ZMK RAM | `0x20000000`–`0x20003FFF` |
| 부트 요청 | `0x20004000` 예약; 상위 RAM을 앱에 할당하지 않음 |

앱 시작 `0x08004000`은 파일의 빈 공간만 보고 추정하지 않고 부트로더의 분기 코드로 확인했습니다. 순정 앱 초기 SP는 `0x20000400`, Reset Handler는 `0x08004239`입니다. 세부 주소와 추출 절차는 [reverse-engineering.txt](../analysis/reverse-engineering.txt)에 있습니다.

## 3. 읽어 나온 UF2와 기록 가능한 UF2는 다르다

최초 `CURRENT.UF2`는 flags와 Family ID가 0이며 부트로더까지 포함합니다. 부트로더 쓰기 경로는 flags `0x2000`, Family ID `0x9D5BCF10`, 256바이트 정렬 주소와 최대 256바이트 payload를 요구합니다. 사용자가 원본을 그대로 복사했을 때 복원되지 않은 현상과 일치합니다.

| 파일 | payload | UF2 크기 | 용도 |
| --- | --- | --- | --- |
| 최초 CURRENT.UF2 | 128 KiB, 512블록 | 256 KiB | 원본 증거, 전체 읽기 덤프 |
| 순정 복구용 UF2 | 앱+설정 112 KiB, 448블록 | 224 KiB | 원본 내용에 업로드 헤더 재구성 |
| ZMK UF2 | 검증된 앱 BIN + 마지막 블록 패딩 | 빌드마다 다름 | 코드 영역만 기록 |

[package_uf2.py](../tools/package_uf2.py)는 벡터·크기·패딩 경계를 검사하고 기존 출력 파일을 조용히 덮어쓰지 않습니다. 복구 모드는 정확한 원본 BIN 해시를 요구합니다. 복구용 payload가 원본과 동일한 것은 확인했지만, 순정 복구 성공을 별도로 보고받지는 못했습니다. **백업 확보와 복구 실증을 같은 것으로 쓰지 않습니다.**

## 4. 매트릭스 복원과 레이아웃

압축 Vial 정의는 플래시 `0x0800F512`의 XZ 700바이트에서 복원했습니다. 1,876바이트 JSON이 14×8 논리 좌표와 배열 옵션을 제공했습니다. [vial-definition.json](../analysis/vial-definition.json), [ansi-matrix.csv](../analysis/ansi-matrix.csv)가 매핑 근거입니다.

실제 스캔은 row/column GPIO가 아닙니다. 순정 `0x0800606C` 초기화와 `0x08006168` 스캔에서 다음을 복원했습니다.

- PB12: 클럭. PB13: 출력과 입력을 바꾸는 양방향 데이터.
- PB9: 채움 극성 판별. PB8: 변형 보드 플래그. 다른 기능과 관계가 있으므로 임의의 미사용 핀으로 간주하지 않음.
- 112회 채움 → 반대 비트 주입 1회 → 112회 읽기/출력/클럭. 합계 225클럭.
- 입력 Low가 활성. PB13 pull-down 시험 결과에 따라 입력 풀 방향 선택.
- 히스토리 `(history >> 1) | (active << 7)`, 239 초과 시 누름, 4 이하 시 해제.

따라서 표준 GPIO matrix 대신 [kscan_unicore.c](../src/kscan_unicore.c)와 테스트 가능한 [unicore_scan_core.h](../src/unicore_scan_core.h)를 작성했습니다. 정확한 외부 IC는 확인하지 않았으므로 일반적인 74HC165 체인이라고 단정하지 않습니다.

ANSI 67개에 분할 백스페이스 `(6,2)`, 분할 좌시프트 `(1,4)`를 더한 **69개 합집합**을 유지합니다. ISO는 엔터 주변 키의 역할을 바꾸고 7u는 없는 하단 위치를 `&none` 처리합니다. 전처리로 16조합을 검사했으며, 실제 패드 쇼트 시험은 사용자 확인으로 별도 기록했습니다. Neo65 CU의 70개 바인딩을 그대로 복사하면 안 됩니다.

## 5. 클럭과 부트로더에서 넘어오는 상태

순정 RCC CFGR `0x00684400`과 PLL 선택 코드를 기준으로 HSI 8 MHz / 2 × 12, SYSCLK 48 MHz, APB1 /2, APB2 /1, USB PLL /1을 설정했습니다. F1 Devicetree의 `usbpre`로 USB 분주를 지정합니다. LINK65의 외부 크리스털 설정은 사용하지 않습니다.

[platform_init.c](../src/platform_init.c)는 C 전역 초기화 이전에 SysTick·pending 상태·USB 주변장치 상태를 정리하고 PA12를 Low로 내려 연결 해제를 유도합니다. 조기 함수에서 커널 서비스나 초기화되지 않은 전역을 사용하지 않습니다. `CONFIG_INIT_ARCH_HW_AT_BOOT`와 코드 파티션 설정도 활성화했습니다.

## 6. CI에서 실제로 막힌 부분

| 문제 | 수정 | 교훈 |
| --- | --- | --- |
| west manifest freeze가 가져오지 않은 비활성 프로젝트에서 실패 | `--freeze --active-only` | 실제 활성 의존성 집합을 기록 |
| config 쪽 공통 keymap include 탐색 실패 | 공통 파일을 모듈 `include/`로 이동 | 사용자 config와 모듈 include 경로를 구분 |
| 링크는 성공했지만 ELF/BIN 비교 실패 | PT_LOAD 전체 패딩 대신 할당된 파일 섹션을 LMA 기준으로 비교 | objcopy의 섹션 사이 채움과 ELF 세그먼트 패딩을 동일시하지 않음 |
| 첫 Git push에 `src refspec main does not match any` | 초기 커밋 생성 후 main push | 브랜치 이름 변경만으로 커밋이 생기지 않음 |

검사 범위를 줄여 통과시키지 않았습니다. 섹션/로드 범위와 RAM 경계 검사는 유지하고, 초기화된 RAM의 플래시 로드 이미지 및 패딩 차이를 회귀 테스트에 추가했습니다. 실패 시에는 ELF/map/config를 진단 아티팩트로 남기고, 성공 시에만 업로드용 UF2를 배포합니다.

빌드 성공 후 exact commit의 Actions를 180초 간격으로 확인했습니다. 실패 원인을 고쳐 다시 push하고, 최종 아티팩트의 해시·ELF/BIN·UF2 재생성 일치까지 확인했습니다. CI 통과는 실기기 정상 동작의 대체물이 아닙니다.

## 7. 첫 실기기 실패: Windows HID Code 10

`02f5fab` 빌드는 VID/PID `1D50:615E`로 보였지만 HidUsb 시작이 Code 10 / `0xC0000001`로 실패했습니다. VID/PID가 보인다고 HID 보고서 처리까지 성공한 것은 아닙니다.

부트로더로 돌아온 장치에서 읽은 스냅샷은 배포 ZMK BIN과 정확히 일치했습니다. 원본 부트로더 16 KiB와 설정 8 KiB도 보존됐습니다. 이 시험에서는 파일 전송 손상을 배제할 수 있었습니다. 키보드 입력 보고서 16바이트·미디어 보고서 13바이트도 16바이트 endpoint 크기 안에 있었습니다.

`771dfc0`에서 두 부분을 변경했습니다.

1. 전체 스캔의 IRQ 차단 제거. 기존에는 지연 설정만 676 us이고 실제 코드 시간은 더해지는 동안 USB가 막혔습니다. 변경 후 클럭 High 펄스 안에서만 IRQ를 차단합니다.
2. HID descriptor/callback 등록을 APPLICATION 93으로 옮겨 USB 연결 94보다 먼저 완료합니다. 이전 기본값은 USB 94, HID 95였습니다.

동시에 반복 스캔만 끈 `usb-diagnostic` 빌드도 준비했습니다. 사용자는 **일반판에서 USB와 키 입력이 정상화**됐다고 확인했습니다. 두 수정을 함께 적용했으므로 어느 하나가 단독 원인이었다고 단정하지 않습니다. 드라이버 삭제·교체 없이 해결됐습니다.

## 8. Caps Lock RGB: 부트로더의 마지막 색이 남음

사용자는 부트로더에서 RGB 색이 변하고, 플래싱 후 마지막 색이 고정되며, USB 전원을 끊으면 꺼진다고 보고했습니다. 초기 ZMK에는 RGB 데이터를 보내는 코드가 없었습니다.

| 순정 주소 | 확인한 역할 |
| --- | --- |
| `0x08009E30` | PB15 출력 설정 |
| `0x08009DB4` | MSB-first 한 바이트 타이밍 전송 |
| `0x08009E40` | 픽셀당 3바이트 전송과 latch 대기 |
| `0x0800635C` / `0x08006370` | GRB 배열 구성 / 검정 전송 |
| `0x080063E8` / `0x0800637C` | HID Caps Lock bit 1 / 색상과 PB14 갱신 |
| `0x0800368` | 부트로더 PB15 색 패턴 및 PB14/PA8 변화 |

[caps_indicator.c](../src/caps_indicator.c)는 POST_KERNEL 91에서 PA8/PB14를 순정과 같이 초기화하고 PB15에 검정 프레임을 보냅니다. 이후 ZMK HID indicator 이벤트를 받아 Caps Lock ON은 RGB 각 32의 흰색, OFF는 검정을 전송합니다. LED 상태는 로컬 키 누름 횟수가 아닌 PC 상태를 따릅니다.

[unicore_rgb_byte.S](../src/unicore_rgb_byte.S)는 확인된 48 MHz에서 순정 바이트 송신 명령어를 재현합니다. 로컬 오브젝트와 최종 ELF의 0x76바이트 명령어 영역이 순정과 동일함을 검사했습니다. 24비트 전송 동안만 IRQ를 막고 300 us latch 대기는 IRQ를 허용합니다. `8f92936`에서 사용자가 정상 동작을 확인했습니다. 정확한 LED 모델과 실제 파형은 계측하지 않았습니다.

**교훈:** MCU 재시작과 외부 부품의 전원 초기화는 다릅니다. 정상 cold boot뿐 아니라 부트로더에서 앱으로 넘어오는 경로에서 외부 LED 상태도 초기화해야 합니다.

## 9. UF2 진입과 복귀 관찰

순정 앱 `0x08006488`은 SRAM `0x20004000`에 `0x9D5BFC2B`를 쓰고 system reset을 요청합니다. TOFU 전용 behavior가 이 규약을 사용하며 플래시를 쓰지 않습니다. Fn + 상단 Delete에 연결했고 사용자가 실제 UF2 진입을 확인했습니다.

Fn + Esc는 ZMK의 `&sys_reset`입니다. 사용자는 이 조작으로 부트로더에서 ZMK로 복귀했다고 보고했습니다. 이 관찰은 보존하되, ZMK가 실행되지 않는 동안에는 ZMK 키맵도 동작하지 않으므로 순정 부트로더의 Fn + Esc 지원을 증명했다고 쓰지 않습니다. 정확한 복귀 조건은 별도 확인 항목입니다.

Neo65 CU의 레이어 단축키 방식을 참고했습니다. 일반 키의 combo 대기 지연을 피하되, 해당 보드의 ROM remap/점프 코드를 가져오지는 않았습니다.

## 10. 검증 결과와 다음 이식 작업

| 기준 | 결과 |
| --- | --- |
| `7538637` / `02f5fab` | 전체 컴파일·링크·패키징 성공, 첫 실기기 HID 실패 |
| `771dfc0` | USB·일반 키 및 선택 패드의 원하는 키코드 확인 |
| `5475ca9` | 추가 분할 키 두 개 정상 확인 |
| `8f92936` | Caps Lock LED 초기화/표시 정상 확인 |
| 현재 사용자 보고 | Fn + Delete UF2 진입 확인, ZMK 복귀 관찰, 체감 입력 씹힘 없음 |

정적 검사와 사용자의 실기기 보고를 구분합니다. 장시간 입력, 반복 연결, 대량 동시 키·수정키 조합, 실제 지연 계측, 순정 복구 성공은 별도 완료 기록이 필요합니다. 아직 확인하지 않은 항목을 실패라고도 단정하지 않습니다.

다음은 개인 키맵 이식입니다. 하드웨어 기본값을 유지하면서 `config/`에 Windows/macOS·홈로우·마우스·Fn 레이어를 좌표 기준으로 옮기고, 69개 transform과 배열 옵션을 검증합니다. 그림 자동 생성은 실제 키맵 이후 추가합니다. Studio·영구 저장은 별도 파티션 및 RAM 검토가 필요한 선택 작업입니다.

## 11. 재사용할 작업 순서

1. 원본 증거·해시·복구 경로를 확보하고 기록 범위를 먼저 제한합니다.
2. UF2 헤더, 실제 앱 진입 주소, RAM 조건을 각각 확인합니다.
3. 클럭과 USB를 검증하고 스캐너가 통신 IRQ를 막지 않는지 봅니다.
4. 압축된 키보드 정의와 실제 스캔 함수를 대조해 좌표를 복원합니다.
5. 첫 실패에서는 장치 readback으로 전송 손상과 런타임 문제를 분리합니다.
6. cold boot와 부트로더 handoff를 모두 시험합니다.
7. 빌드 식별자·파일 해시·실기기 관찰을 연결하고, 추정과 확정을 구분합니다.
8. 기반 하드웨어가 동작한 뒤 개인 키맵과 부가 기능을 추가합니다.
